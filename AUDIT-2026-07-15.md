# Audit — ljh-sh/fio v0.1.0 (vendored fio-3.41 @ commit ed675d3)

## Trust model

**What the tool does.** fio is an I/O benchmark: it generates
configurable synthetic workloads (sequential / random read, write,
read-write mix; various block sizes, queue depths, IO engines) and
reports throughput + latency. Operators invoke it against real
files, block devices, or network mounts to characterize storage
performance.

**Who controls input.** The operator does. fio is invoked from a shell
with command-line flags (`--filename=…`, `--ioengine=…`, `--size=…`,
etc.) and/or a job file (`fio job.fio`). Job files reference paths,
sizes, IO patterns. We do **not** recommend running fio with a job
file from an untrusted source; a malicious job file can point
`--filename=` at any path the operator has write access to (see
finding #7).

**Blast radius.** Limited to:
- **Output surface.** Writes benchmark reports to `--output=path`. The
  operator chooses this path; see finding #6.
- **Filesystem surface.** Writes to `--filename=…` paths. The operator
  chooses these; see finding #7.
- **System calls.** Standard open / read / write / fsync / io_uring /
  ioctl on the operator's behalf. No remote network calls in our
  default config (libcurl / librbd / libnfs / libnbd are disabled).
- **No privilege escalation vector.** fio does not run setuid, does
  not exec external programs (the `exec` engine spawns user-supplied
  shell commands per IO — operator responsibility), and does not
  open privileged ports.

## Severity scale

| Level | Definition |
|-------|------------|
| **HIGH** | Local root / RCE / data loss reachable from default config without auth |
| **MEDIUM** | Requires local user OR untrusted input; bounded blast radius.<br>(This tier is **not used** for v0.1.0 because the trust model puts the operator in full control of all input — see Trust model section. Future audit revisions may surface MEDIUM findings if upstream CVEs land in vendored tree or if new code paths accept untrusted input.) |
| **LOW** | Hardening / hardening-adjacent; no realistic exploit |
| **INFO** | Documented trade-off, vendor stance, or positive finding |

## Findings

### #1 — INFO — Vendor stability
axboe/fio is in active maintenance by a Linux kernel maintainer. The
project ships tagged releases every 6-12 weeks; `fio-3.41` (March
2025) is the most recent. The 20+ year track record gives strong
confidence in the vendor's security posture.

### #2 — INFO — Self-contained static binaries
Every release archive ships a **fully self-contained binary** (verified
by `ldd` on Linux — "not a dynamic executable"; `otool -L` on macOS —
only `/usr/lib` / `/System/Library`). No system library injection
attack surface is reachable through the binary.

### #3 — INFO — `--build-static` rule carve-out (static-build.ruleset)
The ljh-sh `static-build.ruleset` (`mneme/.x-cmd/rule/static-build.rule.yml`)
requires `--disable-shared --disable-dependency-tracking` for vendored-C
autotools projects. fio's custom `configure` accepts **neither** flag
(no autotools). The equivalent knob is `--build-static`, which sets
`-static -Wl,--gc-sections`. We propose amending the rule to recognize
`--build-static` as the equivalent for non-autotools C projects (see
mneme PR forthcoming). Until then, this audit serves as the carve-out
justification.

### #4 — INFO — `--disable-shm` (we set this)
We disable SysV shared memory in `scripts/build.sh` (via
`--disable-shm`). Rationale: minimal perf impact for typical workloads,
eliminates `/dev/shm` interaction surface, slightly smaller binary.
End users who depend on it can build fio themselves.

### #5 — INFO — `--disable-{pmem,rdma,rados,rbd,http,xnvme,libblkio,libzbc,isal,isal64,libnfs,tcmalloc}` (we set these)
Twelve optional engines are explicitly disabled to keep the static
binary portable across Alpine/musl, glibc, macOS, and MinGW. The
disabled engines would each pull in a separate `.so` whose static
archive is not shipped by every distro. End users who need them can
build fio themselves.

### #6 — LOW — `--output` path is operator-chosen, no canonicalization
fio's `--output=path` option writes the report to an operator-chosen
path with no canonicalization. This is by design — fio is a benchmark
tool and the operator owns the filesystem. Not exploitable by
untrusted input unless the operator passes untrusted job files.

### #7 — LOW — Job files can reference any filesystem path the operator has
A fio **job file** (`fio job.fio`) references `--filename=...`,
`--directory=...`, etc. The operator is expected to vet job files
from untrusted sources. This is by design — fio is a benchmark tool.
**Mitigation:** operators should never run `fio <untrusted-job>` as
root.

### #8 — INFO — `posixaio` engine requires glibc<2.34 to link `-lrt`
On glibc<2.34, the `aio_read` / `aio_write` symbols live in librt.
fio's configure auto-detects this and adds `-lrt` to LIBS for
glibc<2.34. On musl + glibc≥2.34 the symbols are in libc and no `-lrt`
is needed. Static-binary fallout on Alpine/musl is zero; on
glibc<2.34 (CentOS 7, RHEL 7) static linking needs `librt.a` from the
`glibc-static` package. **End-user impact: none** for our musl
distribution (which is what we ship).

### #9 — INFO — Build determinism caveat
Our build is **not** byte-for-byte reproducible across toolchains.
gcc 13.3 vs 14.2 produce slightly different code at `-O3`, and
clang-vs-gcc diverge further. Reproducibility is bounded to:
- same source (vendored commit `ed675d3`)
- same configure flags
- same toolchain major version (e.g., gcc-13.x produces byte-identical
  output; gcc-13.x → gcc-14.x may differ)

This is acceptable for the "download, run" use case; users who need
hard reproducibility should rebuild from source.

### #10 — INFO — Engine registration via ELF constructors
Each IO engine self-registers via `__attribute__((constructor))`. A
maliciously-modified engine could run code before `main`. We rely on
the vendored source being byte-for-byte upstream's; see #1 and the
verification recipe above.

### #11 — INFO — `out-of-tree` rule carve-out (custom-configure projects)
The ljh-sh `static-build.ruleset` requires that builds leave
`upstream/` untouched. fio's custom (non-autotools) configure writes
a 2-line wrapper `Makefile` in `$BUILD_DIR` whose body is
`include $(SRCDIR)/Makefile`. Because the upstream Makefile uses
relative paths to source files, `.o` files compile *alongside* source
in `upstream/fio/`. To honor the spirit of the rule, `scripts/build.sh`
ends with a `find $SRC -name '*.o' -delete` cleanup (equivalent to
`make distclean` crossing the in-tree / out-of-tree boundary). After
the cleanup, `upstream/fio/` is byte-for-byte identical to the
upstream tree (153 files, 0 `.o`). This is the same carve-out as the
rule's own amended wording for custom-configure projects
(applied retroactively to this audit per the rule's
"carve-out (custom-configure projects)" sub-section).

## Summary

- **0 HIGH findings** for our build/packaging layer.
- **0 MEDIUM findings** for our build/packaging layer.
- **2 LOW findings** (#6, #7) — both standard benchmark-tool caveats
  documented for operator awareness.
- **9 INFO findings** — vendor stability + carve-outs + design
  trade-offs documented above.

This audit covers the **wrapper layer** (`scripts/`, `.github/`, docs,
NOTICE, LICENSE) and the **static-build configuration** (which
optional engines are enabled, which flags are passed, what is
statically linked). The audit does **not** re-audit fio itself —
that's the upstream maintainers' job, and we inherit their security
posture by pinning `fio-3.41` and refusing to modify the vendored
source.
